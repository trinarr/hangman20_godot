# Постоянные локальные заполнители

## Установка

Клиентская реализация уже находится в репозитории; повторно применять Git-патчи не требуется. Для настройки backend проверьте состояние миграций и примените в Supabase SQL Editor
`supabase/migrations/010_leaderboard_local_fillers.sql` поверх миграций 005–009.
Она обновляет dev и production, не меняя результаты игроков и таблицы имён.
Затем последовательно применяются 011 (профили), 012 (имена) и 013 (внешность
заполнителей). Каждая из новых миграций допускает повторное применение самой
себя; миграции ранних версий поверх более новых не запускайте.
Клиент требует `protocol_version=2`: старый сервер не будет ошибочно принят
за новый. Развёртывание SQL на Supabase не выполняется самим Git-патчем.

## Первый запрос

Клиент передаёт `p_seed_fillers=true`, пока у текущего аккаунта и языка нет
сохранённой начальной подборки. Сервер всегда возвращает реальные строки в `top`.
Если реальных участников с положительными звёздами меньше 100, отдельный массив
`fillers` содержит ровно 100 фейков со звёздами 30–100. Подборка псевдослучайна,
но стабильна для UUID, языка, пула и слота, не зависит от JWT или реальных звёзд.
Пустая реальная таблица также даёт 100 фейков. При 100+ реальных участниках массив
`fillers` пуст; клиент сохраняет факт инициализации и больше фейков не запрашивает.

Имена сохраняют смешивание: ru — 60 СНГ / 40 английских; en — 20 СНГ / 80 английских.
Каждый исходный пул содержит 80 казуальных / 20 сленговых имён. Все эти 100
заполнителей — начальный резерв, а не 100 дополнительных видимых строк.

Каталог `supabase/seeds/leaderboard_filler_nicknames_v3.json` обновляет все 200 имён
под ограничение 2–18 символов без пробелов. Миграция
`012_leaderboard_filler_refresh.sql` применяется после 011 в dev и production:
меняются имена и ограничение длины, сохраняются номера слотов, стили, правила
смешивания, ID фейков и расчёт их звёзд. Проверка генератора:
`python tools/build_leaderboard_filler_refresh.py --check`; запуск без `--check`
пересоздаёт 012 из каталога. Опубликованные 007/008 не перегенерируются.
Применение проверяется локальным `tools/tests/leaderboard_filler_refresh_sql.cjs`.

Каталог сочетает обычные имена, уменьшительные формы, инициалы и числа,
транслит, короткие псевдонимы, отдельные слова и шуточные игровые фразы.
Регистр и разделители намеренно различаются. Казуальная часть не ограничена
генерацией двух слов: этот формат относится к кнопке выбора имени игрока.
Типы основаны на просмотренных примерах из [Candy Crush](https://community.king.com/en/candy-crush-saga/discussion/495912/the-players-who-topped-the-2025-final-leaderboards),
[Reddit](https://www.reddit.com/r/GirlGamers/comments/xotws2),
[Пикабу](https://pikabu.ru/story/pro_nikneymyi_13939662) и
[9GAG](https://9gag.com/gag/aRBEyZB). Их доли в каталоге — редакторский выбор,
а не измеренная статистика этих площадок.

Сохранённые на устройствах подборки продолжают использовать прежние имена:
обновление серверного каталога влияет на новые инициализации. Миграция не очищает
клиентский кеш и не возвращает вытесненных фейков.

Текущий каталог `supabase/seeds/leaderboard_filler_nicknames_v4.json` хранит для
каждого слота `nickname`, `character_id` (1–2) и `frame_id` (1–5). Миграция
`013_leaderboard_filler_appearance.sql` добавляет эти два номера в таблицы
заполнителей обоих окружений с NOT NULL и ограничениями диапазонов; RPC читает
их из таблицы. Начальные значения сохраняют прежнюю внешность, вычислявшуюся
по ID в 011. Проверка: `python tools/build_leaderboard_filler_appearance.py --check`;
без флага генератор пересоздаёт 013 из каталога v4. Каталог v3 и миграция 012
сохраняются как предыдущий шаг.

Клиент дополняет старые подборки без номеров внешности тем же стабильным
вычислением по ID. Имена, звёзды и история вытеснения сохраняются. Строка
глобального рейтинга и закреплённая строка показывают место, аватар с рамкой,
имя и звёзды на подложке валютного счётчика. Все строки одного экрана используют
два общих портретных viewport, принадлежащих экрану, вместо отдельных сцен на
каждого игрока. Геометрия подложки общая с HUD через `resource_counter_style.gd`.

## Слияние и вытеснение

1. Все реальные строки из актуального `top` обязательно входят в локальный список.
2. Из сохранённых фейков выбираются самые сильные на оставшиеся места до 100.
3. Отобранные реальные строки и фейки сортируются по звёздам. Фейки могут быть выше
   игрока. При равенстве звёзд реальные строки идут первыми; их порядок сохраняет
   серверные правила времени достижения и ID. Фейки с равными звёздами — по ID.
4. Слабые вытесненные фейки удаляются из локального резерва навсегда. Их звёзды
   не меняются. При 100 реальных участниках удаляются все оставшиеся фейки.

Например: сначала 2 реальных игрока + 98 фейков, затем 40 + 60, 99 + 1, 100 + 0.
Даже реальный игрок с одной звездой получает место; правило «все реальные входят»
важнее простого выбора 100 самых больших результатов из объединения.
При административном удалении реальных аккаунтов вытеснённые фейки не воскресают,
поэтому список может стать короче 100. При обычном росте числа участников этого нет.

Сервер последующих запросов возвращает только реальные результаты. База не
хранит фиктивные аккаунты, прогресс фейков или персональные списки заполнителей.
Синхронизация звёзд без чтения топа также не запрашивает подборку.

## Сохранение и позиция игрока

Файл `user://leaderboard_<dev|production>_<hash URL>.json` хранит текущий UUID,
отдельные ru/en состояния, активных фейков и последний реальный топ. Запись идёт
через временный файл и переименование. Повреждённый кеш игнорируется. Перезапуск
сохраняет те же имена, звёзды и вытеснение; повторная загрузка получает только
реальных игроков. Очистка данных приложения теряет этот локальный прогресс.

Замена анонимного аккаунта очищает прежнюю подборку. UUID в ответе защищает также
от смены сессии внутри RPC: при необходимости клиент делает ещё один запрос с
инициализацией для нового аккаунта. URL проекта, dev/production и языки изолированы.
При смене языка каждый вариант получает свой начальный резерв и далее хранит его.

В отображаемом топе клиент присваивает места заново, включая фейков, и обновляет
`me.rank`, чтобы закреплённая плашка совпадала с обычной строкой. При 100+ реальных
участниках заполнителей уже нет и действует серверное место / «Топ N%». Фейки не
входят в `total_players` и серверные проценты. Сохраняются положительные реальные
результаты, лучший результат, минутный кеш и принудительное обновление.

## Проверки

```sh
NODE_PATH=<node_modules с @electric-sql/pglite> node tools/tests/leaderboard_local_fillers_sql.cjs
python3 tools/run_content_tests.py --godot /path/to/godot --suite leaderboard_local_fillers
python3 tools/run_content_tests.py --godot /path/to/godot --suite leaderboard
python3 tools/run_content_tests.py --godot /path/to/godot --suite leaderboard_ui
```

SQL-тесты проверяют протокол, 0/99/100 реальных участников, смесь 60/40 и 20/80,
фиксированные звёзды, смену аккаунта, dev-изоляцию, права и повтор миграции.
Клиентские — сохранение после перезапуска, неизменность звёзд, доступ реальных
игроков с низкими звёздами, положение своей плашки, вытеснение без возвращения,
сетевую ошибку, языки, смену UUID внутри RPC и некорректную начальную подборку.
