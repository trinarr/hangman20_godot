# Dev-статистика в одном проекте Supabase

Реализовано поверх коммита `f227c4c`. Лидерборды не добавляются.

## Установка

1. В Supabase SQL Editor выполните `supabase/migrations/004_quiz_statistics_dev.sql` после существующих миграций 001–003.
2. Установите обновлённый клиент. В `project.godot` добавлено `quiz_statistics/dev_enabled=true`.
3. Запустите игру из редактора или экспортируйте debug APK. В логах будет `Environment=dev`, путь RPC `/rest/v1/rpc/quiz_answer_dev` и файл `user://quiz_statistics_dev.json`.
4. Ответьте на викторину. В логах успешной отправки должны появиться HTTP 200 и `Database acknowledged`. Проверьте dev-счётчики в SQL Editor:

```sql
select question_key, counts
from quiz_dev_private.questions
where counts <> array[0,0,0,0]::bigint[];
```

Не добавляйте `quiz_dev_private` в Exposed schemas. Доступ игры идёт через `public.quiz_answer_dev`, а не через открытые таблицы. URL, публичный ключ и настройки анонимной авторизации остаются прежними. Секретный ключ `service_role` клиенту не нужен.

Миграция не выполняется из игры и не применена к облачной базе автоматически. До её выполнения dev-запросы будут получать ошибку отсутствующей функции; переключения на production не произойдёт.

## Выбор окружения

| Запуск | RPC | Локальное состояние |
|---|---|---|
| Редактор / debug | `quiz_answer_dev` | `quiz_statistics_dev.json` |
| Release | `quiz_answer` | существующий `quiz_statistics.json` |
| `tools/run_content_tests.py` | реальная сеть отключена | временный тестовый профиль |

`quiz_statistics/enabled` управляет release, `quiz_statistics/dev_enabled` — dev. Отсутствующее dev-настроечное значение означает `false`; production-настройка его не заменяет. `HANGMAN_SUPABASE_NETWORK_DISABLED=1` запрещает все запросы независимо от сборки и настроек. Для ручной интеграционной проверки запустите обычную debug-сборку без этой переменной.

Перед созданием HTTPRequest транспорт проверяет настройку окружения и точный путь: разрешены только соответствующая RPC-функция, анонимная регистрация и обновление токенов. Debug не может вызвать production RPC через этот транспорт. Это защита от ошибки клиента; публичный ключ и тип сборки не являются серверным механизмом разграничения полномочий.

Смена окружения выполняется только выбором типа сборки. Токены, очередь и временные файлы dev и production разделены. Старый production-файл не импортируется в dev. Кеш и отметки об ответах живут в памяти отдельного запуска. Логика обновления JWT и замены отозванной сессии применяется в обоих окружениях.

## Сервер

`quiz_dev_private.questions` хранит отдельные счётчики. `quiz_dev_private.players` хранит отдельные отметки первых попыток. При создании dev-каталога копируются только ключи вопросов: production-счётчики и игроки не копируются. Позиции битовой маски dev выделяются независимо от production и сохраняются при повторном запуске миграции.

`quiz_answer_dev` имеет тот же контракт, что `quiz_answer`: предварительное чтение счётчиков и признака ответа, отправка ответа, подтверждение без счётчиков при наличии кеша, учёт подсказки без голоса. Все ссылки в dev-функции фиксированно указывают на dev-таблицы; параметра выбора схемы от клиента нет. Прямой доступ ролей anon/authenticated к dev-таблицам закрыт, RLS включён. Вызывать RPC может только authenticated.

Production-функция и существующие данные не изменяются. Supabase Auth, настройки, ресурсы и лимиты остаются общими для проекта. Тестовые анонимные аккаунты видны в общем Auth; удаление пользователя из Auth затрагивает его записи в обоих окружениях, если он использовался в обоих. Для сброса статистики используйте очистку dev-таблиц ниже, без удаления пользователей.

## Обновление каталога и сброс

После добавления production-версий вопросов выполните `supabase/quiz_statistics_dev_sync.sql`. Он добавляет только отсутствующие ключи с нулевыми счётчиками, сохраняет dev-голоса и позиции существующих вопросов. Для изменений структуры/протокола поддерживайте обе серверные реализации одинаковыми; SQL-тест проверяет их соответствие.

Новые dev-счётчики изначально нулевые. Действует общий порог `minimum_answers`: пока голосов недостаточно, заливка не показывается. Для проверки визуала можно вручную задать синтетические счётчики только в dev:

```sql
update quiz_dev_private.questions
set counts = array[5,15,30,50]::bigint[];
```

Сброс dev-голосов и отметок попыток (SQL Editor):

```sql
begin;
update quiz_dev_private.questions set counts = array[0,0,0,0]::bigint[];
truncate table quiz_dev_private.players;
commit;
```

Каталог вопросов не удаляйте и не перенумеровывайте. Перед сбросом закройте тестовые клиенты; их несинхронизированные очереди могут снова отправить голоса после запуска. Для полностью чистого теста удалите `quiz_statistics_dev.json` из пользовательских данных закрытой debug-сборки; production-файл сохраняйте.

## Проверки

- `tools/run_content_tests.py --godot <Godot> --suite quiz_statistics`
- `tools/run_content_tests.py --godot <Godot> --suite quiz_sessions`
- `NODE_PATH=<каталог node_modules с @electric-sql/pglite> node tools/tests/quiz_statistics_sql.cjs`

Проверяются выбор RPC/файла состояния, запрет обхода на production, независимые настройки, сохранение production-сессии, сетевой запрет тестов, JWT/восстановление сессий, SQL-права, независимость счётчиков и первых попыток, повторный запуск миграции и синхронизация новых вопросов. Проверки выполняются локально, без регистрации аккаунтов или отправки голосов в облачный проект.
