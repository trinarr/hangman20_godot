# Открытые проблемы проекта

Это список открытых задач, а не полный аудит каждой функции или развёрнутой инфраструктуры. Дата, среда и границы проверки указаны в соответствующем пункте. Закрытые пункты и история изменений доступны в Git; команды проверок — в [tools/TESTS.md](../tools/TESTS.md).

## 5. Размер главных скриптов

Пункт 5 исходного аудита остаётся открытым. Большая часть создания интерфейса и маршрутизации сосредоточена в `scripts/main_portrait.gd`; также крупны `scripts/main.gd` и `scripts/core/game_state.gd`. Это усложняет поиск зависимостей и локальные изменения, но само по себе не доказывает проблему производительности.

При следующих UI-задачах выделять самостоятельные компоненты по существующим образцам popup, результата и награды. Не совмещать исправление поведения с общей переписью. Сохранять [контракты архитектуры](ARCHITECTURE.md) и проверять жизненный цикл узлов.

## Игровая шапка при 960×1600

05.11.2026: GPU-снимки первого слова в RU при 960×1600 показывают перекрытие персонажа и счётчика попыток верхней панелью. Отдельная контрольная проба с прежним входом через Home воспроизводит ту же геометрию, поэтому это не следствие прямого старта в слово. При 690×1536 перекрытие в проверенных RU/EN-кадрах не наблюдается. Исправление компактной вертикальной раскладки остаётся отдельной UI-задачей; успешные проверки маршрутизации не подтверждают отсутствие этой проблемы.

## Согласие при раннем нажатии на Home

05.11.2026: в контрольном Android release-маршруте через Home кнопка игры становится доступной раньше, чем после полного вступления открывается юридическое согласие. Диагностический вызов действия в этот момент уводит в игру и отменяет отложенное открытие согласия. Новый прямой старт первого слова уже создаёт обязательное согласие под сплешем; прежний маршрут Home требует отдельной проверки реального раннего нажатия и блокировки действий до согласия. Для сравнения скорости автоматизация сначала дожидается согласия и принимает его, затем нажимает игровые кнопки.

## Первое открытие экранов с Home

Остаётся задержка холодного запуска до первого Home: основная сцена с зависимостями загружается и подготавливается до её `_ready()`, затем отдельно проигрывается вступление Home. Готовый кеш глифов не устраняет эту часть запуска. Ускорение отдельных переходов и снятие чёрной заглушки не означают, что общая стартовая загрузка уже решена.

Порционный прогрев двух общих MSDF-профилей уменьшает часть затрат, но задержки построения экранов остаются. Android-проба 05.11.2026: Xiaomi 2109119DG / Android 14 / Adreno 642L, Godot 4.7.2 Mobile/Vulkan, RU, отдельный пакет без рекламы и сетевого доступа. Каждый вариант запускается свежим процессом с одинаковым ожиданием на Home; прогрето 266 пар «шрифт — символ». Максимальный интервал между кадрами за первые четыре секунды после нажатия (мс):

| Экран | Без прогрева → с прогревом | Повтор с обратным порядком |
| --- | --- | --- |
| Слово | 212 → 177 | 167 → 156 |
| Цепочка этапов | 341 → 232 | 280 → 213 |
| Награда | 362 → 306 | 318 → 256 |
| Профиль | 385 → 448 | 324 → 198 |

У профиля большой разброс и разное направление изменения: устойчивый выигрыш не подтверждён. Эти запуски не подтверждают ускорение любого экрана или отсутствие лага при раннем нажатии до завершения очереди. Стоимость других шрифтовых профилей, создания карточек, раскладки, восстановления партии и нативной рекламы остаётся отдельной. Полный APK с рекламой этим измерением не проверен. JSON и журналы находятся в игнорируемом `builds/font-warmup-results/`; корректные снимки — в `pass-2/`. Регрессия `home_font_warmup --gpu` прошла 624 проверки RU/EN × 960×1600/690×1536; также прошли `home_tournament` (36), `home_resource_counters` (32), `resume_flow --gpu` (25), структурные валидаторы и проверка пяти MSDF-профилей.

Холодный старт теперь ожидает локальную подготовку под системным сплешем перед вступлением Home. Отдельный Gradle APK с теми же рабочими скриптами и нативным gate проверен на указанном Xiaomi: RU (266 пар «шрифт — символ»), EN (164), согласие после вступления и уход/возврат из фона. Во всех четырёх процессах подтверждены нативный bridge, снятие сплеша до tween и завершение вступления; ошибок движка/Java нет, снимки просмотрены. От инициализации диагностического autoload до начала вступления прошло 5.4–6.7 секунды; ещё около 1.7 секунды занимает вступление. Это дополнительное ожидание перед показом Home, а не ускорение всех экранов. APK не содержит рекламных SDK/сетевых разрешений; полный релиз не проверен. Итоги и исходные хеши — в игнорируемом `builds/startup-results/`; диагностическое приложение удалено. Финальный `home_font_warmup --gpu` — 673 проверки, `startup_last_chance --gpu` — 86; сценарии согласия/турнира ждут готовности и завершения вступления, а не фиксированного таймера.

Совместимость стартового сплеша с рекламной инициализацией проверена на том же Android в отдельном Gradle APK с рабочим Yandex AAR и `mobileads-mediation:8.6.0.0`, debug/demo-ID. Три свежих процесса: сохранённый отказ от персонализации, отсутствие принятия документов и ответ региона во время прогрева. В первом и третьем SDK стартовал при ещё активном сплеше; во втором до принятия документов не было запроса/готовности SDK, после принятия инициализация прошла. В каждом процессе ровно один `native_configure` и один `sdk_initialized_callback`, тестовый баннер загрузился и показан; ошибок движка/Java нет. Дополнительно прошли `ad_consent` и `home_resource_counters --gpu` (32). Рабочие рекламные скрипты, Java-мост, AAR и боевые настройки не менялись; изменение сплеша не перенесло вызов инициализации из `main.gd:_ready`. JSON, журналы, снимки и хеши сборки — в игнорируемом `builds/startup-ads-results/`. Диагностическое приложение удалено. Боевые показы, все партнёрские сети по отдельности и полноэкранные показы этим прогоном не подтверждены.

Эксперимент с предварительно запечёнными глифами двух общих шрифтов выполнен в копии проекта; рабочие `.import` пока сохраняют `preload=[]`. Штатный импорт Godot сохранил по 149 символов объединённого корпуса UI RU/EN с точными `variation_opentype` рабочих FontVariation, MSDF size/range не менялись. На том же Xiaomi сравнивались два debug APK без рекламных SDK, по три свежих процесса RU/EN на вариант, 12 запусков с чередованием порядка. Пять исполняемых GDScript-ресурсов запуска/шрифтов в APK совпадают побайтно. Прогрев, его порции, сплеш и ожидание фоновых загрузок одинаковы.

| Медиана времени до анимации Home | Текущий импорт | Предварительный рендер | Снижение |
| --- | --- | --- | --- |
| RU, от диагностического autoload | 5.373 с | 3.447 с | 35.9% |
| EN, от диагностического autoload | 4.532 с | 3.368 с | 25.7% |
| RU, от создания Android Activity | 7.257 с | 5.458 с | 24.8% |
| EN, от создания Android Activity | 6.297 с | 5.060 с | 19.6% |

В готовом кеше находились все 266 RU / 164 EN элемента очереди ещё до прогрева. CPU-время вызовов подготовки глифов: медиана RU 1803→8.1 мс, EN 1047→7.4 мс; оставшаяся очередь занимает 0.37–0.46 с из-за порций/кадров. Импортированные ресурсы двух шрифтов выросли со 161778 до 3893570 байт, APK — на 3.49 MiB. На Home счётчик GPU-текстур увеличился на 10.08 MiB; изображения атласов двух фактически используемых RID выросли с 10 до 12 MiB в RU и с 8 до 12 MiB в EN. Медиана PSS после вступления выросла примерно на 4 MiB; это снимки процесса, а не измерение пиков памяти. Кеш подтверждён также на ПК в изолированном профиле. Ошибок движка/Java нет; внешний вид RU/EN просмотрен. Независимое декодирование и системный снимок подтвердили целостность изображения; для просмотра доступны повторно закодированные `*-qa.png` с теми же пикселями. Сырые JSON, журналы, параметры импорта, размеры/хеши ресурсов и сравнение — в игнорируемом `builds/font-prebake-results/`, итог — `comparison.json`. APK и временный проект удалены. Это результат двух профилей на одном Android GPU; release с рекламой и остальные экраны этим сравнением не проверялись. Перед внедрением учитывать рост резидентных текстур и проверить потребителей обоих шрифтов.

## Сравнение прототипов оптимизации иконок

05.11.2026: отдельное диагностическое APK на Xiaomi 2109119DG / Android 14 / Adreno 642L, Godot 4.7.2 Mobile/Vulkan, физический viewport 1080×2400, логический 960×2133. На этапе сравнения рабочие шейдеры и UI не менялись. Эталон использует настоящий `hint_icon_extrusion_shadow.gdshader`: четыре смещённых слоя с квадратом альфы и основную иконку. В предыдущем нагрузочном замере дополнительные слои использовали цветной шейдер с tint; числа ниже относятся к более точному эталону.

- **A — объединённые тени с кэшем обводки.** Исходная обводка один раз рисуется в общий для одинаковых иконок SubViewport с двукратным разрешением; один слой объединяет четыре выборки его альфы. Основная иконка сохраняет действующий шейдер. При изменении масштаба маска обновляется каждый кадр, иначе физическая толщина обводки перестаёт соответствовать эталону. Ключ кэша должен учитывать ресурс, физический размер и толщину; отдельный viewport на каждую строку рейтинга не проверялся и не рекомендуется этим замером.
- **B — отдельная SDF-маска.** Оригинальный RGBA остаётся источником цвета, дополнительная RH16-маска хранит расстояние до контура. Один слой вычисляет обводку и объединяет четыре тени. Маска общая для разных размеров и толщин. Это приближение существующей дилатации по 16 направлениям, а не побайтная замена её изображения.

GPU-время в мс: диапазон медиан двух проходов с обратным порядком вариантов, по 90 измерений после 30 кадров прогрева. При анимации масштаб синхронно менялся от 0.8× до 1.2×; для A указана сумма времени корневого viewport и viewport маски.

| 40 звёзд, статично | 12.28–12.29 | 5.02–5.03 | 2.62–2.64 |

Обновление общей маски A во время анимации занимает около 0.26 мс GPU. Статический кэш одной звезды добавил 246016 байт (около 240 KiB) по счётчику памяти текстур движка, одинаково для 8 и 40 экземпляров. Это один размер и одна толщина; удержание нескольких сочетаний умножает расход. У B четыре подготовленные маски занимают 1.55 MiB данных RH16 без mipmaps: звезда 72 KiB, сердце 72 KiB, еда 288 KiB, галочка 1152 KiB. Это объём текстурных данных, не RSS процесса; размер масок пока не оптимизирован. Все четыре SDF были загружены до замеров, поэтому нулевой прирост в строках нагрузки B не означает отсутствие расхода памяти. Холодная загрузка, первая компиляция и задержка первого построения кэша отдельно не измерены.

Проверены 180 состояний: четыре реальные иконки × масштабы 0.5/1/2 × обводка 2/5/8 px × обычное состояние, альфа ветки 0.5, альфа CanvasGroup 0.5, нулевая альфа и grayscale. Сохранены 540 снимков и три снимка после анимации; выполнено численное сравнение и просмотр обычных и худших случаев. При нулевой альфе оба прототипа полностью исчезают. A ближе к эталону, но повторная фильтрация кэша меняет край тени, особенно при размере 48 px. B заметнее меняет тонкие детали и сглаживание контура на маленьких иконках. Медиана средней абсолютной RGB-ошибки в области иконки/тени среди ненулевых состояний — 1.76/255 у A и 5.29/255 у B; худшие состояния — 6.89 и 24.01 соответственно. Это описательные метрики, не критерий приёмки. В снимке после анимации ошибки — 0.23 и 4.83 соответственно. Первоначальные артефакты SDF устранены до итогового прогона; финальный журнал процесса не содержит `ERROR:`, `SCRIPT ERROR` или `FATAL EXCEPTION`.

**Вывод:** A — более осторожный следующий кандидат для внедрения с ограниченным общим кэшем и проверкой настоящих UI-анимаций. B быстрее A примерно в 1.4–2.0 раза на этой нагрузке и устраняет зависимость кэша от размеров, но требует отдельного решения по изменению контура и уменьшению больших масок. Эти реализации альтернативны: B уже объединяет тени, держать рядом с ним кэш A не нужно. Это не замеры FPS реального экрана; частоты GPU не фиксировались, другие Android GPU и интеграция с UI RU/EN при 960×1600 и 690×1536 не проверены. Нагрузочная анимация использует одинаковый масштаб всех звёзд; стоимость одновременно разных размеров/фаз у A остаётся открытой. Исходники проб, APK, итоговый JSON, метрики и снимки находятся в игнорируемом `builds/icon-prototypes/`; итоговые результаты — `android-final/files/report.json`, сравнения — `comparison-final.png` и `worst-cases-final.png`.

## Доверие к лидерборду

`supabase/migrations/010_leaderboard_local_fillers.sql` принимает клиентский `p_stars` с проверкой диапазона и сохраняет улучшение рекорда. Серверного доказательства заработанных звёзд в этой функции нет. Для защиты соревновательного рейтинга от модифицированного клиента нужен серверный источник начислений либо проверяемый протокол результата. Диагностика развёрнутой БД на чтение выполнена 05.11.2026; этот контракт доверия к клиентскому результату сохраняется.

05.11.2026 в Supabase `Hangman 2.0` выполнены только согласованные диагностические SELECT 01–04. Все 48 проверяемых столбцов и восемь RPC имеют ожидаемые типы/сигнатуры; индексы готовы и валидны, ограничения валидированы. Хеши тел восьми RPC совпадают с последними локальными определениями из 017/018 при CRLF. Приватные таблицы имеют RLS; у anon/authenticated нет прямых прав и USAGE приватных схем. Проверенные агрегаты без нарушений, счётчики population совпадают с положительными игроками; ожидающих блокировок и накопленных deadlock нет. История миграций не зарегистрирована либо не видна: полнота всей последовательности DDL этим не доказана. Данные и настройки сервера не менялись.

Остаются предупреждения Supabase Advisors: EXECUTE для anon у служебной `public.rls_auto_enable` ([описание проверки](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)) и отключённая защита скомпрометированных паролей ([описание](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)). Функция не вызывалась, её фактическая доступность как RPC не проверялась. SECURITY DEFINER для игровых authenticated RPC и отсутствие политик на полностью закрытых приватных таблицах сами по себе не доказывают утечку. Неиспользованный индекс `players_tournament_sample_idx` оставлен до нагрузочного измерения; накопительная статистика не доказывает его ненужность.

Новые ники ограничены на клиенте русскими/английскими буквами с Ё/ё, цифрами 0–9 и одиночными обычными пробелами. RPC `leaderboard_sync` / `leaderboard_sync_dev` в миграции 017 пока проверяют только длину, края и управляющие символы. Для защиты от обхода клиентской валидации нужна следующая миграция с тем же набором допустимых символов; учесть ранее сохранённые имена и старые клиенты.

- Завершить приёмку настоящей release-подписи и доставки AAB по [инструкции Android](../tools/EXPORT.md). Home/профиль RU/EN и настройки EN проверены на телефоне; это не полная матрица UI. Для прозрачности отдельно проверить блики монет/сундука, переключение рекламной кнопки ×2, затухание серых иконок подсказок/темы комментария, аватар при уходе с главного экрана и приглушение отметок использованных букв: проверки материалов и компонентов на настольном GPU не подтверждают все эти переходы на Android.
- Повторять проверку состава пакета при изменении фильтров. Текущие APK/AAB прошли проверку runtime-ресурсов и исключений документации/служебных файлов; это не универсальный поиск любых секретов.
- Уточнить историю применённых миграций и ограничения клиентских API-токенов. Текущие сигнатуры/тела RPC, права/RLS и агрегаты dev/prod сверены диагностикой на чтение; наличие SQL в Git само по себе состояние сервера не подтверждает.
- Подтвердить изоляцию тестового профиля на Linux, если эта среда используется; последний фактический прогон выполнен на Windows.
- Региональный запускатель проверен на Windows 05.11.2026: фактический временный `user://` подтверждается до игровых autoload; IPinfo token удалён, Supabase-сеть отключена. Добавлены отсутствовавшие `symbols`/`scenes`, итоговый PASS проверяется вместе с engine.log. Изоляция и отсутствие ошибок не выводятся из одного кода завершения.

05.11.2026 обязательные GPU-наборы `rewards`, `save_recovery`, `resume_flow`, `runtime_optimizations`, `release_reward_regression` прошли соответственно 297/73/25/49/44 проверки в изолированных профилях. `resume_flow` подтверждает сохранение 50/50 и отсутствие повторных звёзд за скорость после восстановления викторины. На Android процесс остановлен во время фактически показанного Rewarded с незаработанным receipt: после запуска остались 200 монет и лимит 5, ложной выплаты нет. Это не проверка остановки в узком окне после получения reward callback до записи receipt. Незаработанный receipt сохраняется намеренно для позднего callback и сам по себе не является дефектом очистки.

## Границы проверки MSDF-профилей

**Аудит числа профилей 05.11.2026:** 11 сгенерированных ширин заголовка не означают 11 одновременно загруженных профилей. Обычные заголовки используют 35; единственный runtime-подбор другой ширины — `stage_word_input.gd:_resolved_display_font`, общий для слова двух игроков и ника. Он перебирает 35→30 перед уменьшением размера шрифта. Профили веса 760 с ширинами 25–29 вызываются только тестами, их удаление после обновления генератора/проверок не должно менять текущий интерфейс, но не даст экономии runtime-кеша. В диагностическом APK их ресурсы и import-записи занимают 403796 байт (около 0.385 MiB); кнопочный профиль веса 680 / ширины 25 к этой группе не относится.

На Windows / Godot 4.7.2 / D3D12 сравнены текущий подбор и экспериментальные наборы ширин. Геометрия проверена на 15083 уникальных случаях: нормализованные слова из RU/EN-каталогов длиной до 20 и граничные варианты ников длиной до 18, фактические размеры полей/шрифтов 448/40 и 328/31. Для наборов 35/32/30 и 35/30 переполнений и изменений размера шрифта не найдено. Отличаются соответственно 14 и 15 случаев, максимальное сокращение измеренной ширины — 2 и 3 единицы stage. Это не полный перебор произвольного пользовательского ввода. Единственная ширина 35 изменила размер шрифта в 85 случаях, расхождение ширины достигает 14 единиц; этот вариант не рекомендован.

Проба: три общие надписи, последовательный ввод RU/EN, затем показ четырёх реальных строк, выбирающих исходные ширины 34/33/32/31. При обычном наборе только с итоговыми ширинами 35/30 данные атласов составили 9/6/5 MiB, но счётчик GPU-текстур у всех вариантов совпадал: промежуточные профили генерируют глифы при `get_string_size`, однако GPU-загрузка зависит от фактической отрисовки. Поэтому экономию нельзя считать как фиксированное число MiB на каждый удалённый профиль. Указанные GPU-разницы получены в одинаковых пробах при 960×1600 и 690×1536, а не в Android-сборке игры; это не замер RSS/PSS.

Текущая bounce-анимация изменяет масштаб надписи, а не ось ширины шрифта: font выбирается до старта. В шести GPU-прогонах (текущий, три и две ширины × оба размера) проверены начальное, промежуточные и конечное состояния, повторный запуск, неизменность font внутри tween и возврат масштаба к 1; ошибок движка нет. Просмотренные снимки подтверждают небольшое сужение затронутых строк. Переносы здесь не меняются: эти поля однострочные с выключенным autowrap, а обычные заголовки, кнопочный и тяжёлый профили сохраняются. Экспериментальные исходники, корпус, JSON и PNG — в игнорируемом `builds/font-width-audit/`.

## Фоновая загрузка стартовой сцены

При загрузке `Main.tscn` через `ResourceLoader.load_threaded_request` на Windows / Godot 4.7.2 при завершении процесса появляется предупреждение ObjectDB о RefCounted с reference count 0. Минимальная локальная проба только запрашивает и забирает PackedScene, не создавая игровой интерфейс: 84 экземпляра; расширенный сценарий загрузочного экрана также выдаёт это предупреждение. Это воспроизводится без создания/удаления UI и не доказывает утечку узлов загрузчика. Причина и поведение экспортированного Android runtime пока не установлены; число не является измерением байтов или роста памяти при длительной игре. Проверки загрузки проходят без ERROR / SCRIPT ERROR; предупреждение учтено отдельно.

## Приёмка DEV APK

Фактический DEV APK пока не проверен на package ID, локализованное launcher-имя, Firebase app ID, консоль и параллельную установку с release. Проверка имён вызывает методы guard напрямую, без полного Android-экспорта. После сборки помощник проверяет только маркеры нативного splash bridge; автоматической проверки фактических DEV package ID, консоли и Firebase-ресурсов нет. Gradle-политика запрещает сборку пакетов с суффиксом `.dev` в release, но её отдельная проверка без Android-плагина не заменяет приёмку APK на устройстве.

## Проверка стартового UI на Android

Android Back, возврат из браузера и фактический холодный запуск на EN-устройстве локальными GPU-пробами не подтверждены. Холодный сценарий на ПК проверяется без предварительной инициализации Database тестом, включая отдельные языки интерфейса и слов, задержку/ошибку базы, повтор и уход. Проверки звука на ПК подтверждают callbacks, исходные аудиоресурсы и настройку mute; воспроизведение на реальном Android-устройстве отдельно не проверено.
