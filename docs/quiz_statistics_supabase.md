# Контракт статистики викторины Supabase

Источники реализации: `scripts/services/quiz_statistics.gd`, миграции `001`–`004`, `016` и `017` в `supabase/migrations/`. Сервис необязателен: основной игровой результат не должен ждать авторизацию или сеть.

## Подключение

В Supabase используется Anonymous Sign-In. В `project.godot`, раздел `[quiz_statistics]`, задаются URL, клиентский публичный ключ и настройки включения/порогов. Серверные ключи, пароли БД и service-role в приложение не добавляются. Миграции применяются отдельно после проверки состояния сервера; запуск клиента не создаёт схему.

Release использует `quiz_answer`, debug/редактор — `quiz_answer_dev`. Включение и пороги задаются отдельно: `enabled`/`minimum_answers` и `dev_enabled`/`dev_minimum_answers`. Не копируйте числовые значения из отчётов. Подробности dev-данных — в [quiz_statistics_dev.md](quiz_statistics_dev.md), управление JWT — в [quiz_statistics_sessions.md](quiz_statistics_sessions.md).

Dev и production имеют отдельные локальные состояния и очереди. Авторизация также используется лидербордом. `HANGMAN_SUPABASE_NETWORK_DISABLED=1` блокирует реальную сеть; тестовые mocks не отправляют голоса в облако.

До сохранённого завершения вводного обучения и принятия документов общая авторизация и все HTTP-запросы Supabase запрещены. Завершение обучения запускает сетевой worker. Ограничение проверяется также перед созданием `HTTPRequest` и прямой авторизацией, поэтому наличие прежнего refresh token не обходит его.

## Редакции и первая попытка

Ключ редакции включает язык, ID, SHA-256 вопроса, исходных вариантов и правильного индекса. Правка содержания создаёт отдельную статистическую редакцию. Позиции вариантов связываются с каталогом, а не с текущим порядком кнопок.

После миграции `016_compact_storage.sql` таблицы вопросов хранят `language`, `question_id` и `revision_hash bytea` длиной 32 байта с общей уникальностью. RPC по-прежнему принимает прежний текстовый `p_key` (`язык:ID:hex-SHA-256`), поэтому опубликованные клиенты и сохранённые очереди не требуют обновления. `slot`, identity-последовательности, голоса и `seen` сохраняются. Счётчики ответов остаются `bigint[]`.

Предварительное чтение вызывает RPC с `p_answer=-1`; оно не увеличивает счётчики. Учитывается первая попытка аккаунта на редакцию. Использование 50/50 отмечает попытку, но не добавляет голос. Повторное открытие результата или повтор отправки не должны увеличивать статистику второй раз.

Если счётчики уже получены, клиент показывает локальный снимок и может отправить голос без повторной выдачи счётчиков. Без подтверждения запись остаётся в сохраняемой очереди. Неизвестная серверу редакция ждёт обновления каталога и не должна блокировать другие ответы. Детали отображения — в [quiz_statistics_feedback.md](quiz_statistics_feedback.md).

Миграция `017_api_efficiency.sql` сохраняет одиночные RPC и добавляет `quiz_answers(p_answers jsonb)` / `quiz_answers_dev(p_answers jsonb)`. Пакет содержит 1–20 объектов с `p_key`, `p_answer` и необязательным `p_include_counts`. Ответ — `{ok:true,results:[...]}` в исходном порядке; каждый результат повторяет `p_key` и `p_answer`, содержит `ok` и при успехе обычные поля одиночной RPC. Некорректная запись или неизвестная редакция получает `ok:false,code:"22023"`; остальные записи обрабатываются. Неожиданная ошибка БД откатывает весь пакет. Первая попытка остаётся идемпотентной даже при повторе целого пакета или дублирующихся ключах.

Клиент отправляет одиночный запрос для одной записи и пакеты для накопленной очереди. До удаления записей проверяет состав и порядок ответа, а при недоступности новой RPC (HTTP 404 / `PGRST202`) возвращается к одиночной отправке. Подтверждённая запись удаляется только при совпадении ключа и отправленного ответа: превращённое во время HTTP предварительное чтение в настоящий голос не теряется. Предварительное чтение (`p_answer=-1`) на сервере получает позицию, счётчики и `seen` одним запросом без создания игрока.

Порог отображения и условие использования статистики для 50/50 различаются: показ допускает сумму не меньше порога; выбор двух наименее популярных неправильных ответов требует суммы строго больше порога. Правильный ответ всегда сохраняется. При отсутствии данных используется обычный случайный выбор.

## Обновление каталога

`python tools/build_quiz_statistics_catalog.py` генерирует `supabase/quiz_statistics_catalog.sql` для схемы после миграции 016; `--check` проверяет актуальность без записи. Историческая миграция `002_quiz_catalog.sql` больше не перезаписывается. После проверки SQL новые production-ключи добавляются на сервер до выпуска контента; dev синхронизируется через `supabase/quiz_statistics_dev_sync.sql`. Оба инструмента сохраняют прежние позиции и счётчики, dev-синхронизация не копирует production-голоса.

На существующей БД с миграциями до 015 сначала применяют только `016_compact_storage.sql`. Она уже преобразует существующий каталог обоих окружений; повторная загрузка каталога для этого не нужна. Для новой БД миграции выполняют последовательно. Старые миграции поверх 016 повторно не запускают.

Для оптимизированного API после 016 применяют `017_api_efficiency.sql`, затем обновляют клиент. Прежние клиенты продолжают использовать одиночные RPC. Миграция 017 инициализирует точные счётчики участников под блокировкой записи в рейтинги, добавляет триггеры и новые RPC; ожидание блокировки ограничено 5 секундами. После применения обновлённый `01_schema.sql` проверяет шесть RPC и таблицы `population`; `03_data_aggregates.sql` позволяет сопоставить `population.total` с `players.positive_scores`.

Миграция 016 выполняется одной транзакцией, берёт эксклюзивные блокировки и переписывает таблицы (включая `CLUSTER` каталога для освобождения места от удалённого текстового ключа). Запускайте её в период низкой нагрузки с запасом дискового места на переписывание. При ожидании блокировки более 5 секунд или неожиданном старом формате ключа транзакция прерывается; исправление причины и повторный запуск выполняются отдельно. После ошибки в SQL Editor завершите прерванную транзакцию командой `ROLLBACK`, прежде чем повторять запуск. После применения используйте обновлённые отчёты `01_schema.sql` и `03_data_aggregates.sql` и сравните их с исходными снимками.

Не очищайте каталог и не переиспользуйте позиции `slot`: отметки первых попыток привязаны к ним. Добавление ключей должно сохранять прежние голоса и отметки. Состояние уже подключённой БД проверяется до выполнения SQL; секреты авторизации и полные auth-ответы в журналы не выводятся.

Проверки `quiz_statistics` и `quiz_sessions` запускаются через [tools/TESTS.md](../tools/TESTS.md). Доступность RPC, применённые миграции и права рабочего сервера проверяются отдельно.
