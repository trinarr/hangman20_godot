# Лидерборд по звёздам: сервер, клиент и debug-логи

Патч поверх `0cd6c57` с уже применённой правкой отдельных dev/release minimum_answers и разрешённым конфликтом main_portrait.gd. UI не добавляется. Статистика викторин и её пороги сохраняются.

## Установка и проверка

1. Примените основной патч лидерборда, патч процентов и патч серверных заполнителей.
2. В Supabase SQL Editor выполните `supabase/migrations/005_leaderboard.sql`, затем `supabase/migrations/006_leaderboard_percentile.sql`, затем `supabase/migrations/007_leaderboard_fillers.sql`, затем `supabase/migrations/008_leaderboard_filler_mix.sql`, затем `supabase/migrations/009_leaderboard_positive_stars.sql`. Миграция 008 уже включает обновлённые 200 ников; отдельная загрузка JSON не нужна. Она создаёт production и dev одновременно. Скрипт безопасно повторять: результаты сохраняются.
3. Не добавляйте `leaderboard_private` / `leaderboard_dev_private` в Exposed schemas. Игре доступны только public RPC-функции, таблицы закрыты.
4. Запустите debug-сборку с принятыми игровыми юридическими документами. После запуска автоматически отправится сохранённое число звёзд и один раз загрузится топ для логов. Если документы ещё не приняты, проверка повторяется раз в 30 секунд, без регистрации аккаунта до принятия.
5. Заработайте звёзды. Сервис отправит новый общий результат примерно через секунду после последнего изменения. Обычная отправка не скачивает весь топ.

Ожидаемые логи (точное место только в первой сотне):

```text
[Leaderboard] Startup: environment=dev configured=true
[Leaderboard] Sync: stars=150 include_top=true
[QuizStatistics] HTTP POST /rest/v1/rpc/leaderboard_sync_dev
[QuizStatistics] HTTP response: status=200 ...
[Leaderboard] Top received: rows=... (maximum=100)
[Leaderboard] Top: rank=1 player=... stars=... is_me=...
[Leaderboard] Own result: rank=... player=... stars=...
# Если игрок вне топ-100:
[Leaderboard] Own result: Top 6% player=... stars=... total_players=10000
```

Логи содержат только числовой публичный ID участника, место, звёзды, окружение и технический статус. JWT, refresh_token и сырые тела ответов авторизации не выводятся. Все диагностические логи выключены в release.

Проверка dev-данных через SQL Editor:

```sql
select player_id, stars, reached_at
from leaderboard_dev_private.players
order by stars desc, reached_at, player_id
limit 100;
```

До применения миграции RPC будет возвращать ошибку отсутствующей функции; результат сохраняется для повторной отправки. Перехода на production из debug нет. Облачная миграция не применяется автоматически из игры.

## Что хранится

Одна строка на участвующий анонимный аккаунт в каждом окружении:

- `player_id`: публичный числовой ID для будущего UI, передаётся строкой в JSON;
- `user_id`: UUID аккаунта из JWT, используется только сервером;
- `stars`: лучший достигнутый баланс звёзд;
- `reached_at`: время достижения этого результата на сервере.

История партий и всех отправок не хранится. Имён и аватаров пока нет. ID локален для окружения: `123` в dev и `123` в production могут обозначать разных игроков.

Сортировка: звёзды по убыванию, время достижения по возрастанию, затем `player_id` для стабильного разрешения точных совпадений. Места уникальны: 1, 2, 3… При равенстве звёзд выше тот, кто достиг результата раньше. Повторная отправка того же результата или меньшего не сбрасывает время и не понижает рекорд. Нулевой результат не создаёт участника. Существующие записи с нулём не удаляются, но не участвуют в списке, месте и проценте. До первой отправки чистое чтение не создаёт строку.

Индекс соответствует порядку топа. Список возвращается с серверным LIMIT 100. Позиция своего игрока считается на сервере по числу стоящих выше записей. Для мест 1–100 возвращается точное место; вне первой сотни точное место не возвращается, вместо него — `top_percent`.

Процент = `ceil(100 × место / число участников)`, целое число от 1 до 100. Округление вверх означает, что игрок действительно входит в указанную лучшую долю списка. Например, место 600 из 10 000 — «Топ 6%», место 1247 — «Топ 13%», место 101 — «Топ 2%». Последний участник — «Топ 100%». Место 100 всегда отображается точным числом, независимо от процента. Если участников не больше 100, все получают точные места.

Участники — записи текущего окружения в таблице лидерборда с положительным рекордом звёзд. Заполнители никогда не входят в `total_players` и расчёт процента. Аккаунты из Auth без такой записи не учитываются. Dev-процент считается только среди dev-участников. Точный промежуточный ранг, общий размер таблицы, своё положение и топ читаются в одном SQL statement snapshot. Подсчёт общего числа участников и числа стоящих выше может быть дороже самого получения топа при большой базе. Клиент не скачивает остальных участников.

Это рекорд по балансу `GameState.get_stars()`, а не отдельный счётчик всех когда-либо заработанных звёзд. Изменения GameState и правил начисления не вносятся.

## Серверный контракт

Production: `public.leaderboard_sync(p_stars bigint default null, p_include_top boolean default true, p_language text default 'en')`.
Dev: `public.leaderboard_sync_dev` с теми же параметрами.

- `p_stars=null` / параметр отсутствует: только чтение;
- положительное число: создать или улучшить личный рекорд; ноль принимается как отсутствие нового результата;
- `p_include_top=false`: вернуть подтверждение и собственную строку без списка;
- `p_include_top=true`: при наличии положительных рекордов вернуть 100 строк — реальных участников и недостающие заполнители; иначе пустой список;
- `p_language=ru`: 60% заполнителей СНГ + 40% США/Европы; `en`: 20% СНГ + 80% США/Европы. Язык выбирает оформление и пропорции, а не отдельный рейтинг. Доли считаются от недостающего числа строк с округлением до целого.

```json
{
  "ok": true,
  "language": "ru",
  "total_players": 10000,
  "me": {"player_id": "123", "nickname": "Игрок 123", "is_filler": false, "stars": 150, "rank": null, "top_percent": 13},
  "top": [{"player_id": "8", "nickname": "Игрок 8", "stars": 9000, "rank": 1, "is_me": false, "is_filler": false}]
}
```

`me=null` означает, что у аккаунта ещё нет положительного рекорда. У участника топ-100 `me.rank` — число 1…100, `me.top_percent=null`; вне топ-100 `me.rank=null`, `me.top_percent` — целое 1…100. `total_players` возвращается и при чтении, и при отправке без топа; при отсутствии положительных рекордов он равен 0, `top=[]`, `me=null`. Поле `top` отсутствует при `p_include_top=false`. UUID пользователей и время достижения не возвращаются. Топ и своё положение читаются в одном SQL statement snapshot. Создание/обновление атомарно, повторная отправка безопасна.

Функции определяют пользователя через `auth.uid()`, запрещают вызов без авторизации, проверяют типы и диапазон 0…2 000 000 000. Прямые чтение/запись таблиц и доступ к последовательностям закрыты для anon/authenticated, включён RLS. Это техническая валидация, не защита от накрутки: клиентский результат считается доверенным, как согласовано.

## Клиентский API для будущего UI

Автозагрузка `Leaderboard`:

```gdscript
Leaderboard.leaderboard_ready.connect(func(snapshot: Dictionary, from_cache: bool):
    # snapshot.top: максимум 100 строк; snapshot.me: своя строка или null.
    # me.rank != null: точное место; иначе перевести «Топ N%» из me.top_percent.
    pass
)
Leaderboard.sync_failed.connect(func():
    # Можно оставить старые данные и показать кнопку повторной загрузки.
    pass
)
Leaderboard.refresh()      # Кеш до 60 секунд, затем сервер.
Leaderboard.refresh(true)  # Принудительная загрузка.
var snapshot := Leaderboard.cached_snapshot()  # Независимая копия; до первой загрузки может быть {}.
```

`GameState.stars_changed` автоматически передаёт общий баланс сервису. Частые изменения объединяются таймером; хранится только наибольший ожидающий результат. Новый результат, пришедший во время запроса, отправляется следующим запросом. Сетевые ошибки сохраняют ожидающее значение в памяти и повторяются каждые 30 секунд. После перезапуска актуальный результат восстанавливается из обычного игрового сохранения: отдельная растущая очередь событий не нужна. Несохранённые игровые изменения, как и раньше, могут потеряться при аварийном закрытии.

После отправки звёзд кеш списка считается устаревшим, но старый список остаётся доступен через cached_snapshot. Собственная строка обновляется из подтверждения. После первого снимка кеш содержит максимум 100 строк и отдельную собственную строку. Чтения объединяются при активном запросе; кеширование — в памяти текущего процесса. Постоянной подписки Realtime и периодического скачивания топа нет.

В debug один снимок топа загружается при старте сервиса, чтобы видеть работу без UI. В release автоматически отправляются звёзды, но загрузка топа начинается только через refresh. Перед принятием документов и при отключённом backend запросов нет. При смене языка интерфейса кеш списка не переиспользуется; запоздалый ответ для прежнего языка не передаётся потребителям, вместо него загружается текущий пул.

## Общая сессия и разделение окружений

`Leaderboard` отвечает за звёзды, кеш и сигналы. Существующий `QuizStatistics` предоставляет общий авторизованный транспорт: `leaderboard_rpc`. Он использует ту же сохранённую сессию и тот же mutex, что викторины. Параллельные запросы не создают второй аккаунт и не обновляют один refresh_token одновременно. Ожидающий лидерборд получает ход между запросами офлайн-очереди викторин, затем очередь викторин продолжается.

Существующая обработка истечения JWT и отозванной сессии применяется к обоим сервисам. При замене аккаунта кеш лидерборда очищается, текущие локальные звёзды отправляются под новым аккаунтом. Прежний серверный рекорд не переносится и автоматически не удаляется: старый и новый анонимные аккаунты — разные участники. Без привязки постоянного аккаунта устранить такие дубли надёжно нельзя. Отложенные голоса старого аккаунта в викторинах по-прежнему отбрасываются.

| Сборка | Таблица | RPC | Настройка включения |
|---|---|---|---|
| Release | leaderboard_private.players | leaderboard_sync | leaderboard/enabled |
| Debug / редактор | leaderboard_dev_private.players | leaderboard_sync_dev | leaderboard/dev_enabled |

URL и публичный ключ берутся из существующего quiz_statistics-раздела. Настройки включения лидерборда независимы от включения викторин. В патче оба окружения включены. При отсутствии соответствующего значения backend отключён. HANGMAN_SUPABASE_NETWORK_DISABLED=1 отключает все реальные запросы, включая прямой вызов транспорта. Debug-транспорт отвергает production RPC до создания HTTPRequest; release отвергает dev RPC.

Auth и лимиты общие для проекта, данные раздельные. Новый dev-лидерборд пуст, production-игроки не копируются. Пользователя из Auth не удаляйте для сброса dev: это удалит его строки в обоих окружениях.

Сброс только dev-лидерборда:

```sql
truncate table leaderboard_dev_private.players;
```

Не используйте RESTART IDENTITY, если старые публичные ID могли сохраниться у клиентов. Закройте debug-клиенты перед сбросом: при следующем запуске они снова отправят свои звёзды.

## Локальные проверки

```bash
python3 tools/run_content_tests.py --godot <Godot> --suite leaderboard
python3 tools/run_content_tests.py --godot <Godot> --suite quiz_sessions
python3 tools/run_content_tests.py --godot <Godot> --suite quiz_statistics
NODE_PATH=<node_modules с @electric-sql/pglite> node tools/tests/leaderboard_sql.cjs
```

Godot-проверки используют изолированные сохранения, запрет сети и ответы в памяти. SQL-проверки запускают PostgreSQL-совместимый PGlite локально: до 10 000 участников, предел топа, собственное место в первой сотне, проценты вне неё, границы округления, ничьи, повторные отправки, отдельные dev-данные, права и повторяемые миграции. Проверки не создают аккаунты и не отправляют результаты в облачный Supabase.
