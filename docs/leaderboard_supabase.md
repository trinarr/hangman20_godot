# Контракт лидерборда Supabase

Источники текущей реализации: `scripts/services/leaderboard.gd`, `supabase/migrations/005_leaderboard.sql` и последующие миграции до `015_leaderboard_filler_schema_repair.sql`. Проверяйте фактически применённые миграции отдельно: игра не развёртывает сервер автоматически.

## Настройка и окружения

Сначала настройте [общую авторизацию статистики](quiz_statistics_supabase.md). URL и публичный ключ используются общие, включение лидерборда задаётся отдельными `leaderboard/enabled` и `leaderboard/dev_enabled`.

Release использует `leaderboard_sync` и `leaderboard_private`; debug/редактор — `leaderboard_sync_dev` и `leaderboard_dev_private`. Параметры окружения выбирает клиент по типу сборки; это защита от ошибочного маршрута, а не серверная граница полномочий. `HANGMAN_SUPABASE_NETWORK_DISABLED=1` блокирует реальный транспорт в тестах.

Все обращения к Supabase (включая anonymous signup, обновление JWT, статистику и рейтинг) закрыты до сохранённого завершения вводного обучения и принятия документов. Событие завершения обучения запускает синхронизацию сразу; звёзды берутся из текущего сохранённого прогресса. До открытия этого доступа клиент также не выдаёт сохранённый рейтинг и серверный ID в UI.

## RPC и данные

Обе функции принимают `p_stars`, `p_include_top`, `p_language`, `p_seed_fillers` с одинаковой семантикой:

- `p_stars=null` — без изменения рекорда; при отсутствии профильных параметров это чтение. Положительное значение создаёт или улучшает личный рекорд. Повторный или меньший результат не снижает рекорд и не меняет время достижения.
- В рейтинг входят положительные результаты. Сортировка: звёзды по убыванию, время достижения и `player_id` для устойчивого разрешения равенства.
- `p_include_top` управляет выдачей списка реальных лидеров; клиент не скачивает всё население. В первой сотне возвращается место, вне неё — `rank: null`, и интерфейс показывает `100+`. Миграция 014 ограничивает подсчёт предшественников сотней и убирает расчёт процентиля в dev/prod. Поле `top_percent` остаётся зарезервированным для совместимости протокола v2: `100` вне первой сотни и `null` внутри. Новый UI его не использует; прежние кеши и ответы старого сервера поддерживаются.
- `p_language` задаёт оформление начальных заполнителей. Заполнители не являются реальными участниками и не входят в население/проценты.
- `p_seed_fillers` запрашивает начальную персональную подборку; клиент сохраняет её локально. Контракт `protocol_version=2` и правила смешивания описаны в [leaderboard_local_fillers.md](leaderboard_local_fillers.md).

Рекорд относится к переданному балансу звёзд, а не к отдельному серверному счётчику всех заработанных звёзд. SQL проверяет авторизацию и диапазон значения; доказательство игрового результата отсутствует. Это [открытый риск аудита](PROJECT_AUDIT.md).

## Публичный профиль игрока

Миграция `011_player_profiles.sql` добавляет отдельную приватную таблицу `profiles` в каждом окружении. Она хранит `user_id`, `nickname` (2–18 символов без внешних пробелов и управляющих символов), `character_id` (1–2), `frame_id` (1–5) и `updated_at`. Идентификаторы персонажей соответствуют существующему `settings[5]`; порядок рамок закреплён в `scripts/core/player_profile.gd`. Профиль может существовать без положительных звёзд и не создаёт участника рейтинга.

RPC принимает три дополнительных необязательных параметра: `p_nickname`, `p_character_id`, `p_frame_id`. Передаются все три либо ни одного. Старые вызовы с четырьмя параметрами продолжают работать и не стирают профиль. Передача профиля обновляет его даже при `p_stars=null`; время достижения рекорда при этом не меняется. Профиль определяется только через `auth.uid()`, прямой доступ к таблицам закрыт, RLS включён.

Строки `top`, `me` и начальные `fillers` возвращают `nickname`, `character_id`, `frame_id`. Для прежних участников без профиля сохраняется имя `Игрок N` / `Player N`, персонаж 1 и рамка 4. Миграция 013 закрепляет внешность каждого заполнителя в таблице `fillers`; начальные номера совпадают с прежним вычислением по публичному ID. Версия протокола остаётся 2: новые поля дополняют прежний контракт, старые локальные подборки без них принимаются.

После 011 применяется `012_leaderboard_filler_refresh.sql`: все 200 имён заполнителей заменяются каталогом v3 с лимитом 2–18 символов. Слоты, стили и языковые пропорции сохраняются; реальные профили не меняются. Подробности обновления и поведения прежнего клиентского кеша — в [контракте заполнителей](leaderboard_local_fillers.md).

Кнопка «Сохранить» сначала записывает профиль через `GameState` (формат сохранения 5, последовательные миграции 3→4→5). При отказе записи изменения откатываются, окно остаётся открытым. После успешной записи интерфейс обновляется и лидерборд ставит профиль на отправку после обучения. Повторный запуск отправляет локальный профиль заново; сетевой сбой сохраняет запрос для повторной попытки. Изменение во время запроса не теряется после подтверждения старого значения. Это синхронизация с устройства на сервер, а не восстановление сохранения из облака.

При первом запуске без имени `GameState.ensure_initial_player_profile()` создаёт ник из RU/EN-каталога, назначает Лаки (1) и синюю рамку (3) и сохраняет их. Повторный запуск не меняет имя. Аватары скрыты до завершения обучения. Сохранённые до формата 5 имена считаются выбранными пользователем; миграция не перегенерирует их и не меняет внешность.

Формат 5 хранит `player_name_is_custom`, исходную `player_name_base` и применённый `player_name_server_id`. Первый ответ с собственной числовой строкой `me` добавляет ID к исходному автоматическому нику и ставит обновлённый профиль на отправку. Повтор ответа не дублирует суффикс; смена аккаунта заменяет прежний автоматический суффикс. Изменение только персонажа/рамки не делает имя ручным. Сохранение отредактированного или сгенерированного пользователем ника защищает его от поздних ответов, включая перезапуск. Нередактируемое поле открытого попапа получает автоматическое обновление; изменённый черновик не перезаписывается. Если исходное имя с ID длиннее 18 символов, имя сохраняется без добавления номера.

Кнопка случайного выбора в редакторе создаёт ник из двух слов без пробела и без серверного ID, даже если номер игрока уже известен. Такой выбор считается пользовательским и защищён от автоматического добавления ID. RU/EN-каталоги находятся в `data/profile_nicknames.json`; предел — 18 символов, каждая генерация исключает текущий ник. Общий генератор сохраняет поддержку необязательного числового суффикса, но кнопка редактора его не передаёт.

Перед выпуском клиента проверьте состояние сервера и примените только отсутствующие миграции по порядку. После 013 применяются `014_leaderboard_rank_boundary.sql` и `015_leaderboard_filler_schema_repair.sql`. Профильные параметры требуют как минимум 011. Старые миграции поверх более новых запускать нельзя; локальная проверка не применяет SQL в подключённой базе.

### Восстановление после `42703: column f.character_id does not exist`

Функции 013/014 читают сохранённую внешность из `fillers.character_id` и `fillers.frame_id`. Если функция обновлена без табличной части 013, PostgreSQL может принять определение PL/pgSQL, но первый вызов завершится ошибкой 42703. `p_seed_fillers=false` не помогает: столбцы разрешаются для всего SQL-выражения до фильтрации строк.

Для такого состояния применяется **015**, а не старая 013 поверх новой функции 014. Миграция добавляет отсутствующие столбцы в обоих окружениях, заполняет только NULL прежними детерминированными ID внешности и восстанавливает ограничения. Она сохраняет имена, стили, существующую внешность, реальные профили, результаты, права и определения RPC; логика `100+` из 014 остаётся действующей. Повторное применение безопасно. После применения повторите загрузку рейтинга либо перезапустите клиент: при сетевой ошибке клиент сохраняет ожидающий результат.

## Обновление и проверка

Для сверки фактической схемы, прав, RPC и агрегатов сервера используйте [диагностический пакет только на чтение](../supabase/diagnostics/README.md). Его запросы не применяют миграции и не вызывают игровые функции.

При изменении RPC поддерживайте dev/prod-контракты согласованными; не запускайте старую миграцию поверх более новой. Для существующего сервера применяйте только отсутствующие миграции после проверки состояния и прав. Не открывайте клиенту прямой доступ к приватным таблицам.

Локальные сценарии `leaderboard`, `leaderboard_local_fillers`, `leaderboard_ui` запускаются через [контентный запускатель](../tools/TESTS.md) с mock-транспортом. Для проверки работающего backend отдельно проверьте авторизацию, чтение до первого рекорда, улучшение/повтор рекорда, заполнители и разделение окружений. Локальный тест не подтверждает RLS развёрнутой БД.
