# Диагностика Supabase без изменения данных

Пакет снимает состояние PostgreSQL для Hangman 2.0. Каждый `.sql` — один самостоятельный `SELECT`, возвращающий одну строку с полем `audit_report` в формате JSON. Запросы не создают объекты, не изменяют данные/права/настройки, не сбрасывают статистику и не вызывают игровые RPC. Это **диагностика**, её не нужно добавлять в список миграций.

SQL проверен локально через PGlite в транзакциях `READ ONLY`: на актуальной, частично обновлённой и пустой базе, с административными и ограниченными правами. Это подтверждает работу запросов на тестовых состояниях, а не состояние рабочего сервера. В подключённом Supabase пакет автоматически не выполнялся.

## Файлы

| Файл | Результат |
| --- | --- |
| [01_schema.sql](01_schema.sql) | Наличие и типы игровых столбцов, сигнатуры/перегрузки RPC, история миграций при доступности, таблицы, RLS-флаги, метаданные ограничений, индексов и триггеров |
| [02_access.sql](02_access.sql) | Эффективные права `anon`, `authenticated`, `service_role`, доступ к схемам, таблицам, последовательностям и пользовательским функциям, `SECURITY DEFINER`, `search_path`, метаданные политик |
| [03_data_aggregates.sql](03_data_aggregates.sql) | Число записей, диапазон результатов, нарушения форматов/диапазонов, дубли, заполнители, агрегаты статистики викторины; без выгрузки отдельных игроков |
| [04_health.sql](04_health.sql) | Версия PostgreSQL, выбранные несекретные параметры, размеры, накопительная статистика, количества соединений/ожидающих блокировок, расширения и публикации игровых таблиц |
| [05_rpc_source_private.sql](05_rpc_source_private.sql) | Дополнительный **приватный** экспорт определений четырёх игровых RPC, политик, ограничений, индексов, default-выражений и представлений |

В основных отчётах `01–04` нет исходников SQL, отдельных ников, пользовательских UUID, email, `seen`-битовых карт, ключей вопросов, паролей или JWT. Из таблицы истории миграций берутся только номера версий, без текста команд. `auth.users`, сессии, Vault и значения секретов не читаются. Размеры/количества и минимальный/максимальный баланс являются агрегатами, не анонимизированной выгрузкой игроков.

Файл `05` читает код, а не исполняет его. Если на сервере кто-либо вручную прописал секрет или идентификатор конкретного человека внутри SQL, он может попасть в этот экспорт. Перед передачей `05` вне своего компьютера просмотрите текст и удалите такие значения. Для первоначальной диагностики достаточно `01–04`.

## Запуск в Supabase Dashboard

1. Откройте нужный проект в [Supabase Dashboard](https://supabase.com/dashboard). Сверьте проект: оба наших окружения обычно находятся в одной базе, в отдельных схемах; каждый запрос собирает dev и production вместе.
2. Откройте **SQL Editor → New query**. Задайте имя, например `Hangman audit 01 schema`.
3. Откройте `01_schema.sql` из этого каталога и скопируйте **весь файл** в SQL Editor. Выполняйте его с административным доступом к своей базе, обычно ролью `postgres`; роль записывается в отчёт. При ограниченных правах часть данных будет недоступна либо отфильтрована RLS — это будет отмечено.
4. Нажмите **Run**. Не подставляйте ключи, пароли, токены или `user_id`: у запросов нет входных параметров.
5. В результате должна появиться одна строка `audit_report`. Экспортируйте результат в CSV средствами таблицы результатов либо скопируйте **полное содержимое ячейки** в локальный файл `01_schema.json`. Снимок экрана не сохраняет длинные определения и массивы целиком.
6. В отдельных запросах выполните `02_access.sql`, `03_data_aggregates.sql`, `04_health.sql` и сохраните результаты под соответствующими именами. `03` делает точные проходы по игровым таблицам; выполняйте его в период низкой нагрузки. При timeout сохраните ошибку как непроведённую проверку, не принимайте её за нулевые значения и не увеличивайте лимиты сервера автоматически.
7. Если нужен разбор кода сервера, выполните `05_rpc_source_private.sql` и сохраните результат отдельно. SQL внутри результата — исходный код для чтения, его не нужно повторно исполнять.
8. Сохраните дату/время и результаты в одной локальной папке аудита **вне репозитория**. Отчёты содержат сведения о внутреннем устройстве сервиса; их не нужно коммитить или включать в Android-сборку.

Если строка результата отображается сокращённо, используйте экспорт/копирование содержимого ячейки. Для передачи подходят и `.json`, и исходный CSV с колонкой `audit_report`; не обрезайте начало/конец JSON. При SQL-ошибке сохраните имя файла, код и полный текст ошибки; остальные файлы можно запускать независимо. Новые версии интерфейса могут показывать SQL-запросы через Explorer → Run SQL: выбирайте источник **Database**, не Logs.

Не запускайте вместо диагностики файлы из `supabase/migrations`, `quiz_statistics_dev_sync.sql` или SQL-регрессии: они изменяют данные/схему.

## Как читать статусы

| Статус | Значение |
| --- | --- |
| `OK` | Конкретная структурная проверка прошла либо агрегат прочитан без RLS-фильтра текущей роли. Это не заключение о полной безопасности |
| `MISSING_TABLE` / `MISSING_COLUMN` | Нужный объект отсутствует. Именно так проявляется пропущенная табличная часть миграции 013 |
| `TYPE_MISMATCH` / `SIGNATURE_MISMATCH` | Тип столбца или аргументов RPC отличается от ожидаемого клиентом |
| `MISSING_RPC` / `REVIEW_OVERLOADS` | RPC нет либо существует несколько перегрузок, которые нужно проверить на неоднозначность PostgREST |
| `INSUFFICIENT_PRIVILEGE` | У роли SQL Editor нет доступа. Это не означает, что таблица пуста |
| `FILTERED_BY_RLS` | Агрегат вычислен только по видимым текущей роли строкам. Его нельзя принимать за полный объём базы |
| `NOT_REGISTERED_OR_NOT_VISIBLE` | Таблица учёта миграций не найдена. При ручном выполнении SQL это возможно даже при наличии всех игровых объектов |
| `UNEXPECTED_RELATION_KIND` | Вместо ожидаемой обычной/секционированной таблицы найден другой тип объекта; его содержимое не читалось |

Наличие номера миграции не подтверждает наличие всех её изменений. `rpc_checks.status=OK` проверяет сигнатуру, а не правильность тела функции; для сравнения кода есть отпечатки и отдельный файл `05`. Невалидные значения и дубли перед исправлением нужно сопоставить с действующим контрактом. Старые редакции вопросов могут быть нужны сохранённым отметкам первых попыток: пакет ничего не предлагает удалять автоматически.

В отчёте прав отдельно учитываются права на схему, таблицу, RLS и выполнение функции. Проверка SQL-прав не доказывает доступность объекта через HTTP: список **Exposed schemas**, настройки API и поведение PostgREST сверяются отдельно. Клиентский publishable/anon key сам по себе не является секретом; его наличие не заменяет проверку прав. `anon` без сессии и пользователь Anonymous Sign-In с ролью `authenticated` — разные случаи.

`04_health.sql` содержит текущий снимок и накопительные счётчики с `stats_reset`; это не статистика за последние сутки. NULL в `pgrst_db_schemas` не означает пустой список API-схем: сверяйте Dashboard. Нулевой счётчик ошибок в приложенных журналах также не доказывает отсутствие ошибок вне их периода хранения.

## Что дополнительно сохранить из Dashboard

Заполните [settings_checklist.md](settings_checklist.md). SQL не получает полную конфигурацию Auth/API, тарифные лимиты, резервные копии, код Edge Functions и журналы HTTP. Приложите выводы **Security Advisor / Performance Advisor**, время их запуска и журналы ошибки `42703`, если она ещё возникает. Журналы сохраняйте с датами, маршрутом RPC, статусом и кодом ошибки, без `Authorization`, cookies, JWT, refresh token и тел запросов с пользовательскими значениями.

По результатам можно составить список подтверждённых расхождений с кодом, их серьёзность, следующую миграцию/правку и повторную проверку. Аудит не применяет исправления автоматически.

## Локальная регрессия пакета

Из корня проекта, при доступном Node.js и `@electric-sql/pglite` (при необходимости задайте `NODE_PATH`):

```powershell
node tools/tests/supabase_diagnostics_sql.cjs
```

Тест создаёт только БД в памяти, выполняет все пять файлов внутри `READ ONLY`, проверяет целостность данных/определений RPC, пропущенную 013, пустую базу, недостаточные права, RLS-фильтрацию и отсутствие тестовых персональных/секретных значений в результатах. Он не подключается к Supabase.

Официальные справки: [диагностика БД](https://supabase.com/docs/guides/observability/inspect), [Advisors](https://supabase.com/docs/guides/observability/advisors), [журналы и наблюдаемость](https://supabase.com/docs/guides/observability), [история миграций CLI](https://supabase.com/docs/reference/cli/supabase-inspect-db-role-configs).
